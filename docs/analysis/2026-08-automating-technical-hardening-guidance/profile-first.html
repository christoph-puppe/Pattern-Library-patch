Profile-first

In this approach, the rule is an assessment objective part on a control and the check is an executable assessment method part beside it, carrying a script body. Both are added by the catalog when its author supplies the check, and by a profile otherwise.

1. The stakeholder mapping

Three readings of what a hardening rule is are on the record, and this approach reads it as a requirement, as the catalog approach does. What differs is the construct: an assessment objective part on the control rather than a control of its own, added by the catalog or a profile. That is what decides the table below.

Seven parties touch a hardening rule between a published guide and an audited system, and each works in an OSCAL model. Two sets of them are grouped: the bodies that author guidance, and the automation.

2. Strengths and risks with this approach

Considerations when attaching executable assessment methods to controls in a catalog or a profile have been captured

2.1 Strengths4

  1. The check travels with the requirement

    A profile can add parts, props, links and params to a control, so a third party attaches a check to a catalog it does not own.

  2. Parameters feed the script

    A control's params reach the body as environment variables, so one script serves many controls and every organisation its own value.

  3. Findings need no new field

    The method links to an assessment objective, so a finding targets an objective id that every consumer built for 800-53A already reads.

  4. The plan of record does not grow

    The methods sit on controls the assessment plan reads, so a guide with hundreds of checks adds no control to the system security plan.

2.2 Risks4

  1. The catalog becomes code

    A profile resolved from a URL and executed is a remote code path into every assessed system, with the profile author as its operator.

  2. The vocabulary has no owner

    Language, evaluation and pass condition are conventions in a placeholder namespace, and an executor that does not know them can run nothing.

  3. The subject is matched by convention

    The platform prop is a CPE and nothing on an SSP component carries one, so which host runs a check is decided outside the schema.

  4. The claim never meets the result

    The finding targets the objective and the response the control, so the plan of record cannot say which checks its claim rests on.

3. Tracing rules and checks from implementation to assessment

The chain starts where the rule is introduced and runs to the claim and the result. What a step costs is how many relationships it is made of and how each one resolves.

  1. Rule, as it is introduced. The rule is an assessment objective part, added to the framework control by a profile. Every step below starts from that part id. profile, alters[].adds[].parts[].id.
  2. Rule →to Check. Both parts sit in one alter, and the method links to the objective by id, inside one document.
  3. Rule →to Control. The parts are added to the control the alter names. Placing them is the tie, and no second identifier exists.
  4. Check →to Runtime. The props name an engine by a token and say how to judge its result. The executor that honours them is outside OSCAL.
  5. Runtime →to Claim. The run writes no response. The plan of record is untouched by design, so nothing joins the check to the owner's claim.
  6. Runtime →to Result. The observation names the host and carries the raw output as evidence, so two machines behind one component can disagree.
  7. Result →to Control. The finding targets the objective the profile added, so a result reads against the framework with no plan of record.

This site makes no recommendation. It states four approaches in the terms their proponents use and shows what each one has published.
