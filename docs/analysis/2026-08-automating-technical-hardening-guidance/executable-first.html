Executable-first

The rule is an assessment objective part on a control and the check an executable assessment method beside it, carrying a script. The catalog adds both when its author supplies the check, a profile otherwise; a typed assembly on a component is the other construct.

1. Stakeholder roles and OSCAL models

Executable-first treats a hardening rule as a requirement, as catalog-first does, in the Control layer. What differs is the construct: an assessment objective part on the control rather than a control of its own, added by the catalog or a profile. The table shows the models each party uses.

Seven parties publish, implement or assess hardening guidance. The table maps each party to OSCAL models and groups guidance authors separately from automation providers and operators.

2. Strengths and risks

Considerations when attaching executable assessment methods to controls in a catalog or a profile have been captured

2.1 Strengths4

  1. The check travels with the rule

    A profile adds parts to a control, so a third party attaches a check to a catalog it does not own.

  2. Parameters feed the script

    A control's params reach the script as environment variables, so one script serves many controls with each organisation's own value.

  3. Findings need no new field

    The method links to an assessment objective, so a finding targets an objective id every 800-53A consumer already reads.

  4. The plan of record stays put

    Methods sit on controls the assessment plan reads, so hundreds of checks add no control to the plan of record.

2.2 Risks4

  1. The catalog becomes code

    A profile resolved from a URL and executed is a remote code path into every assessed system, operated by the profile author.

  2. The vocabulary has no owner

    Language, evaluation and pass condition are conventions in a placeholder namespace, and an executor that does not know them runs nothing.

  3. The subject is a convention

    The platform prop is a CPE that no SSP component carries, so which host runs a check is decided outside the schema.

  4. Claim and result never meet

    The finding targets the objective and the response the control, so the plan of record cannot name the checks behind its claim.

3. Tracing rules and checks from implementation to assessment

The chain connects a rule to checks, implementation claims and assessment results. Each step identifies the relationships a consumer must resolve and the fields used to resolve those relationships.

  1. Rule definition. The rule is an assessment objective part, added to the framework control by a profile. Every step below starts from that part id. profile, alters[].adds[].parts[].id.
  2. Rule →to Check. Both parts sit in one alter, and the method links to the objective by id, inside one document.
  3. Rule →to Control. The parts are added to the control the alter names. Placing them is the tie, and no second identifier exists.
  4. Check →to Runtime. The props name an engine by a token and say how to judge its result; the executor is outside OSCAL.
  5. Runtime →to Claim. The run writes no response, and the plan of record is untouched, so nothing joins the check to the owner's claim.
  6. Runtime →to Result. The observation names the host and carries the raw output as evidence, so two machines behind one component can disagree.
  7. Result →to Control. The finding targets the objective the profile added, so a result reads against the framework with no plan of record.

No recommendation is made. The analysis compares four approaches and the published OSCAL content.
